1. ภาพรวมและ Flow ทั้งระบบ

ระบบไม่มีฐานข้อมูลหลักถาวร — state เก็บเป็นไฟล์ใน storage/app/poc (Laravel) และ /data/poc (Python) ผ่าน Docker volume ร่วมกัน. Elasticsearch ใช้เป็น index สำหรับค้นหา, MongoDB เก็บ blob เอกสาร, Redis เป็นคิว.

หัวใจ: หน่วยข้อมูลพื้นฐานคือ “block” ทุก block มี 4 ชั้นข้อความ เสมอ: raw_text (ดิบจากการสกัด) → normalized_text (จัดไทยแล้ว) → ai_suggested_text (AI แนะนำ) → approved_text (คนอนุมัติ). และ chunk คือหน่วยที่ใช้ค้นหา ซึ่งสร้างจาก block เหล่านี้ตอน export.

3. Normalize + Spellcheck ภาษาไทย

ฝั่ง Fast path หลังสกัดเสร็จจะ dispatch NormalizeDocumentJob (ไม่ล้ม ถ้า Python ดับก็ข้าม) ส่ง block ที่ไม่ใช่ตาราง/รูปไปที่ POST /pipeline/normalize แล้วเขียนกลับด้วย ReviewStore::applyNormalizationResults().

  • Normalize (thai_normalizer.py): จัดเรียงสระ, แก้วรรณยุกต์, ํา→ำ, ล้าง whitespace
  • Spellcheck (thai_spellchecker.py): Norvig + resources/legal_terms.txt — ทำเฉพาะ block ที่ needs_review=true
  • Autocorrect: normalize_autocorrect_min_confidence (ปัจจุบันตั้ง 0.85) — คำแนะนำที่มั่นใจ ≥85% จะแก้อัตโนมัติ

4. การทำ Chunk (RAG)

“chunk” คือหน่วยที่นำไปค้นหา. ขั้นตอนการสร้าง:

  1. ตรวจทานทั้งเอกสาร — หน้า /documents/:id/review ใช้ TipTap (DocumentEditorShell.vue) แก้ไขแล้วเซฟเป็น draft_html
  2. จัดกลุ่มเป็น section — หน้า /documents/:id/rag (RagManageWorkspace.vue) รวม block เป็น “section” ตาม chunk_type ผ่าน composables/useLawSections.ts (buildSections). ผู้ใช้เลือกประเภทหัวข้อ (TITLE / ARTICLE=มาตรา / CLAUSE=ข้อ / CHAPTER=หมวด …), รวม/แยก/ลบบล็อกได้
  3. Export → chunks — ExportService::export() เรียก DocumentHtmlService::buildChunksFromHtml(draft_html) ตัดเป็น chunk ต่อ block (จับด้วย data-block-id) แต่ละ chunk มี: chunk_id, page_no, block_ids, section_path, text, meta.type, meta.html → เขียนเป็น export JSON
โครงสร้าง 1 chunk (โดยย่อ): { chunk_id, page_no, block_ids[], section_path, text, meta:{ type, html, layout } }. v1 จับคู่ block 1:1 (การ merge/split/new ทำในหน้า RAG ก่อน export).

สัญญา (schema) ของ chunk export อยู่ที่ schemas/export-rag.schema.json.

5. การทำ Index เข้า Elasticsearch

เมื่อกด “บันทึกและเผยแพร่” จะ dispatch IngestRagJob:

  1. ถ้ายังไม่มี export → เรียก ExportService::export() (สร้าง chunks ตามข้อ 4)
  2. เรียก LawIndexer::index(documentId) — อ่าน export chunks + law_meta แล้วสร้าง ES doc ต่อ chunk ด้วย buildDoc() ยัดเข้า index ชื่อ laws

ฟิลด์ที่ index (จาก LawIndexer.php / LawIndexDefinition.php) เช่น:

กลุ่มฟิลด์ใช้ทำอะไร
ค้นข้อความtitle, text, keywords_text, section_pathfull-text search + highlight
autocompletetitle_suggest, keywords_suggest, section_path_suggest (search_as_you_type)คำแนะนำแบบพิมพ์ไปเจอไป
กรอง (facets)law_type, status, change_status, agency, law_group, signer_group, published_yearตัวกรองด้านซ้าย + สถิติ
สิทธิ์access_scope (public/private), law_idกรองเอกสารส่วนตัว + รวมผลต่อกฎหมาย

6. ระบบค้นหา (Search / Suggest / Fuzzy / Highlight)

Endpoint: POST /api/laws/search, POST /api/laws/suggest, GET /api/laws/facets (ดู routes/api.php).

สถาปัตยกรรม 2 ชั้น (สำคัญ)

LawSearchController::search() ใช้ ผลจากไฟล์เป็นหลัก (authoritative) แล้วเสริมด้วย Elasticsearch:

fileBasedSearch()อ่าน status/บล็อกจริงผ่าน ReviewStore::listLawMeta() — สะท้อนสถานะ publish ล่าสุดเสมอ ไม่พึ่ง ES
+
LawSearchService (ES)ให้คะแนน/จัดอันดับ + fuzzy + facets
→
รวมผลES ที่มีคะแนน + เติมเอกสารที่ ES ตกหล่นจากฝั่งไฟล์

ทำไมต้องมีฝั่งไฟล์: ถ้า ES ยังไม่ได้ index (เช่น dev หรือ ES ดับ) การค้นหายังทำงาน — และตรรกะ fuzzy จริงอยู่ที่ฝั่งไฟล์ด้วย จึงค้นเจอแม้ ES ว่าง.

ค้นหาแบบตรงตัว + คำใกล้เคียง (Fuzzy)

  • ตรงตัว: ฝั่งไฟล์ใช้ mb_stripos บนชื่อ/เนื้อหา; ES ใช้ multi_match best_fields
  • คำใกล้เคียง (พิมพ์ผิด): ถ้าตรงตัวไม่เจอ จะ fallback — ฝั่งไฟล์ใช้ Dice-similarity แบบ multibyte (รองรับไทย, sliding window) ใน fileSearchMatch/textSimilarity; ES ใช้ fuzziness: AUTO. ตัวอย่าง “มหาวิทยาลับ” → เจอ “มหาวิทยาลัย”
  • ผลลัพธ์แนบ fuzzy / meta.mode=file_fuzzy เพื่อให้ UI ขึ้นแบนเนอร์ “แสดงผลใกล้เคียง”

ไฮไลต์คำ (Highlight)

ฝั่งไฟล์คืน title_highlighted (ครอบคำที่ตรงด้วย <mark>); ES คืน highlight ของ text/title/keywords เป็น snippets. ฝั่งหน้าเว็บ sanitize ด้วย DOMPurify แล้วเรนเดอร์.

คำแนะนำ (Suggest / autocomplete)

LawSuggestService: bool_prefix บน *_suggest fields ก่อน ถ้าไม่เจอค่อย fuzzy fallback. ใช้ทั้งในกล่องค้นหา /database และกล่อง hero หน้าแรก.

7. Redis & คิวงานเบื้องหลัง (Queue)

ในระบบนี้ Redis ทำหน้าที่เดียว: เป็น “คิวงานเบื้องหลัง” (queue backend) ของ Laravel — จากคอนฟิกจริง QUEUE_CONNECTION=redis (ส่วน CACHE_STORE=file และ SESSION_DRIVER=file ไม่ได้ใช้ Redis).

laravel-appโยนงาน (dispatch) เข้าคิว แล้วตอบผู้ใช้ทันที
→
Redisกล่องพักงาน (queue)
→
queue-workerphp artisan queue:work ดึงงานมาทำทีละงาน (tries=2, timeout=1800)

งานหนักที่วิ่งผ่านคิว (โฟลเดอร์ app/Jobs/):

Jobทำอะไร
ExtractDocumentJobสกัดเอกสารหลังอัปโหลด (แยก Fast/Standard)
NormalizeDocumentJobจัดภาษาไทย + spellcheck
CorrectDocumentJobแก้คำ / AI correction (เส้นทาง standard)
ReprocessBlockJobสกัดบล็อกใหม่รายบล็อก
IngestRagJobexport chunks + index เข้า Elasticsearch
ทำไมต้องมีคิว: (1) ไม่บล็อกผู้ใช้ — อัปโหลดเสร็จได้ response ทันที ส่วน OCR/สกัดที่กินเวลาทำเบื้องหลัง; (2) ขยายกำลังได้ — docker compose up -d --scale queue-worker=3 ทำหลายเอกสารพร้อมกัน; (3) กันงานหาย — worker ล้ม งานยังอยู่ใน Redis ให้ retry. ถ้า Redis ดับ งานเบื้องหลังหยุด แต่หน้าเว็บ/ค้นหายังทำงาน (ไม่พึ่ง Redis).

8. การทำ Cache — ทำไม doc โหลดเร็ว

ระบบเก็บข้อมูลเป็นไฟล์/Mongo (ไม่มี DB หลัก) การอ่านซ้ำ ๆ จึงแพง — เลยมี cache 3 ชั้น ทำให้หน้ารายการ/ค้นหา/เปิด doc เร็ว:

ชั้นอยู่ที่ไหน / เก็บอะไรล้าง (invalidate) เมื่อไหร่
1. Laravel cache
file driver		 ReviewStore::listLawMeta() ใช้ Cache::remember('law-meta-list', 180, …) — cache รายการ meta ของกฎหมายทั้งหมด (ชื่อ/สถานะ/หน่วยงาน/ปี…) ไว้ 180 วินาที. หน้า /database (ค้นหา + facets) และ dashboard อ่านจากตรงนี้ จึงไม่ต้องเปิดอ่าน review blob ทุกอันทุก request MongoBlobStore เรียก Cache::forget('law-meta-list') ทุกครั้งที่มีการเขียนเอกสาร (insert/update) → ข้อมูลสดเสมอหลังแก้
2. Frontend cache
in-memory Map		 resources/js/stores/reviewCache.ts — เก็บใน browser: reviewCache (ReviewDocument ต่อ id) และ previewCache (HTML พรีวิว). เปิด doc/พรีวิวซ้ำ = ดึงจาก Map ไม่ยิง API ใหม่. ยิ่งกว่านั้น ReviewPage ยัง อุ่นพรีวิวไว้ล่วงหน้า (getPreviewCached() ทำงานเบื้องหลัง) ให้ก้าวถัดไปรู้สึกทันที ล้างเมื่อเซฟ/แก้เอกสาร (reviewCache.set ใหม่ + previewCache.delete) — พรีวิวจะถูกสร้างใหม่จากข้อมูลล่าสุด
3. PHP OPcache
bytecode		 apps/app-laravel/docker/opcache.ini — cache bytecode ที่คอมไพล์แล้ว ของไฟล์ PHP (memory 256MB) ให้รันเร็วขึ้น ไม่ต้องคอมไพล์ใหม่ทุก request Dev: revalidate_freq=60 (เช็ค mtime ทุก 60 วิ). Deploy: php artisan optimize แคช config/route เพิ่ม
ภาพรวมว่าทำไมเร็ว: หน้ารายการ/ค้นหาเร็วเพราะ law-meta-list ถูกแคช 180 วิ (ชั้น 1); เปิด doc/พรีวิวเร็วเพราะ browser จำไว้ + อุ่นล่วงหน้า (ชั้น 2); ตัว PHP เองเร็วเพราะ OPcache (ชั้น 3). ทั้งหมดมีกลไกล้าง cache เมื่อข้อมูลเปลี่ยน จึงไม่แสดงข้อมูลเก่าค้าง.
